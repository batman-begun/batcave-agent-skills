# Existing repositories and portfolio

## Adoption (audit first)
1. Inventory root, tracked files, branch, dirty work, native build/publish commands, architecture/canon, existing documentation, tests/CI, external dependencies, security/privacy classification and collaborators. Use available tools; report inaccessible parts. Do not read sensitive data unnecessarily.
2. Map eight roles to existing authoritative files, note competing sources, stale information and missing evidence. Identify profile obligations and risk. Score per requirement PRESENT / PARTIAL / MISSING / NOT APPLICABLE (with reasons). Distinguish observable and declared controls.
3. Propose minimal reversible mapping: prefer adding indexes/manifests, no physical moves unless necessary. Preserve native layout, existing host instructions, branch and Git history, relative links, asset references, URL paths, build/deploy pipelines. Don't replace existing AGENTS.md blindly: merge nonconflicting guidance, flag conflict. Provide affected files, dependency impact, verification and rollback plan. Obtain authorization for migration and sensitive remote actions.
4. On authorized branch/worktree, record baseline, apply incremental changes, run prior checks before/after where possible, verify moved references and downstream artifact identity; keep unrelated changes. Do not rewrite history or delete original work unrequested. Rollback plan must not destroy user modifications. Commit only within permission, report actual revision.
5. Check structural and substantive requirements, compare behavior against baseline, update manifest and state, document migration decisions and limitations. No production deployment by implication. If structural incompatibility with an existing repo policy cannot be resolved, retain existing structure and report partial compliance.

## Portfolio / master index
Optional separate private Git repo (not required for individual UPR). Registry entries: stable project_id, title, profiles, lifecycle, repo locator, authoritative state relative path, last observed revision/time, visibility/access class, relationships with typed edges, shared skill version and optional public-safe abstract. Use links to children rather than copied full records. State in index is a cache with observation date; project state and actual artifact baseline remain canonical. Cross-project constraints are versioned shared policies adopted explicitly by each child, never silently override local approved constraints. Store credentials in separate service, not index. Respect differing permissions between projects; avoid exposing private names/metadata in public index. A single repo may host multiple projects only if boundaries, IDs and authority are clear. Use local paths or any Git provider, no hard dependency on GitHub.

OMNI/LUMOS or other project memory systems can read/write authorized project records via adapters; designate one canonical location per data type. Migrating away requires inventory/export, compare record counts/IDs and spot-check semantics, resolve conflicts, verify access and restoration before decommissioning. No automatic retirement or deletion. Indexing/search, embeddings, notifications, orchestration, subagent runtime and permission enforcement are separate capabilities; Git alone supplies history and versioned storage, not those capabilities.

## Portability
Canonical Markdown, JSON-compatible YAML, plain-text formats and source. Document how to bootstrap locally, recover history, retrieve external assets and reconfigure provider-specific hooks. Make export/backup with access control and verify restore periodically. Treat hosting-specific CI/workflows as adapters, keep local checks runnable where possible. Record skill version and schema changes, preserve migration notes. Do not introduce a new service solely to meet generic template.
